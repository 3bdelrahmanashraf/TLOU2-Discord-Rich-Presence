WHAT THE MOD DOES
-----------------
It publishes a Discord Rich Presence status for The Last of Us Part II
Remastered: the current chapter, which character is being played, difficulty and
run modifiers, collectible count, and playtime.

It reads the game's own save metadata (params.json, plus the NTFS last-access
time of the save slots so that loading a save from the menu is reflected
immediately). It does not modify saves, does not read process memory, does not
inject into or hook the game, and writes nothing outside its own folder except
the Discord presence itself, which is sent over Discord's local named pipe.
There is no network traffic other than that local pipe.

Python standard library - no pip packages. The user installs Python 3 from

The Discord application ID inside it is stored XOR/base64-encoded so that end

whole helper is readable and it is functionally the same file that is in the
repository.

BUILD STEPS
-----------
Windows 10/11 x64, PowerShell 5.1, mingw-w64 and any Python 3 on PATH.

  git clone https://github.com/3bdelrahmanashraf/tlou2-discord-rich-presence.git
  cd <repository>
  copy config.json.example config.json
  powershell -NoProfile -ExecutionPolicy Bypass -File .\pack.ps1 `
    -Gcc "C:\path\to\x86_64-w64-mingw32-gcc.exe"

The build script:
  1. compiles the plugin and the proxy with

       x86_64-w64-mingw32-gcc -O2 -shared -static-libgcc -Wl,--image-base=0x140000000 -o TLOU2DiscordRPC.asi dll\launcher.c
       x86_64-w64-mingw32-gcc -O2 -shared -static-libgcc -Wl,--image-base=0x140000000 -o avrt.dll dll\avrt_proxy.c dll\avrt_stubs.S dll\avrt_proxy.def

     (I used w64devkit 2.11.0, GCC 16.2.0, x86_64-w64-mingw32 target),
  2. reads config.json, XORs it with 0x5A, base64-encodes it, and substitutes it
     into tlou2_rpc.py for the shipped copy,
  3. runs the shipped script once as a smoke test and fails if it cannot build a
     presence (on a machine with no TLOU2 saves it exits with "no usable save
     found", which the build accepts - there is simply nothing to read, and a
     reviewer's PC will normally be in that state),
  4. refuses to package if a config.json, a runtime folder or a nested archive is
     present, then zips with pinned timestamps.

The build is reproducible. The compiler commands pin the PE image base, because
w64devkit's linker otherwise randomises it on every run and that alone changes
the header checksum and every absolute pointer in .data. Building the repository
as-is produces both binaries with SHA-256

  TLOU2DiscordRPC.asi  CD8685FE54DDFF3824DFC92CB75E42CE81C0608B9ECEC75AE54FC6EDEC84F27E
  avrt.dll             5486A747329FC3DA69726CDCDFFA57ACCD946A290E97B719B5B72286F9DA2F5E

identical to the ones in the upload, so you can verify the binaries you received
against the source you can read. I checked this by building from two separate
copies of the repository: both produced the same archive hash. The archive hash
differs from a build of the public repository only because the template carries
a placeholder Discord application ID: the published build embeds my own ID, one
string inside the settings blob, which does not affect any executable code.
Zipping with that one string restored reproduces the uploaded archive byte for
byte.

WHY THERE IS A DLL AND AN .asi
------------------------------
The game imports AVRT.dll from Windows but the install has no ASI loader, so an
.asi alone never runs. avrt.dll is a 44 KB proxy that loads the genuine
System32\avrt.dll, resolves its 20 exported functions into a jump table, and on
a background thread loads TLOU2DiscordRPC.asi from the game folder. The .asi
waits 2.5 seconds, starts the Python helper, and returns. Neither file patches
the game executable or hooks any game function: the proxy only forwards Windows
AVRT calls, and the plugin only spawns a process.

would be grateful if the files could be reviewed on the basis of the above and
the public source rather than the heuristics alone.
